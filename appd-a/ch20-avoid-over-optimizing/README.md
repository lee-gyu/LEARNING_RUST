# ch20. 지나친 최적화의 유혹 피하기

Rust의 대여 검사기는 복사 없는(zero-copy) 코드, 할당 없는 코드를 안전하게 쓸 수 있게 해 줍니다. 입력을 빌려 가리키기만 하는 타입을 만들어도 댕글링 참조가 생기지 않으니, 모든 타입에 참조를 담고 모든 `clone()`을 지우고 싶어지기 쉽습니다. 게다가 Rust에서는 복사와 할당이 `.clone()`, `.to_string()`, `.to_vec()`, `Box::new()`처럼 코드에 그대로 보여서 더 눈에 밟힙니다. 이 챕터는 그 유혹을 이기는 **판단의 순서**를 다룹니다. ① 먼저 데이터를 소유하는 단순한 설계로 쓰고, ② 그 설계의 복사가 어디서 몇 번, 얼마만큼 일어나는지 세고, ③ 문제가 될 만하면 재고, ④ 측정이 가리키는 곳만 바꿉니다. 그리고 복사를 아낀 설계가 부르는 쪽에서 무엇을 빼앗는지(보관, 반환, 스레드로 넘기기, 입력 버퍼 재사용)를 같은 타입의 빌린 판과 소유한 판으로 나란히 봅니다.

- 원제: [Item 20: Avoid the temptation to over-optimize](https://effective-rust.com/optimize.html) (David Drysdale, *Effective Rust*)
- 패키지: `er-ch20-avoid-over-optimizing`
- 확인한 툴체인: rustc 1.100.0, cargo 1.100.0 (2024 에디션)

## 1. 학습 목표

이 챕터를 마치면 다음을 할 수 있습니다.

1. 상태로 보관하는 타입에 빌린 데이터를 담으면 부르는 쪽이 잃는 일(줄 버퍼 재사용, 함수에서 돌려받기, 다른 스레드로 넘기기, 여러 개 모아 두기)을 설명하고, 같은 타입을 소유한 판으로 바꿔 라이프타임 매개변수를 없앨 수 있다.
2. 코드에 보이는 복사·할당의 횟수와 크기를 세어 비용을 가늠하고, 타입마다 `clone()` 한 번이 하는 일(비트 복사, 새 버퍼 할당, 카운트 증가)을 구별할 수 있다.
3. 여러 곳이 큰 데이터를 함께 가져야 할 때 라이프타임 매개변수나 통째 복제 대신 `Rc`/`Arc` 공유 소유로 설계하고, 스마트 포인터가 마지막 수단이 아닌 이유를 설명할 수 있다.
4. 릴리스 빌드, `black_box`, 반복 측정으로 두 판의 경과 시간을 비교해 측정의 함정을 피하고, 측정이 가리키는 곳만 바꿔(받을 때는 빌리고 보관할 때만 복사) 타입의 설계를 지킬 수 있다.

## 2. 핵심 개념

2.1절에서 판단의 순서를 정리하고, 2.2~2.5절에서 지침마다 "문제 상황 → 비권장 코드 → 권장 코드 → 지침을 따르지 않아도 되는 경우" 순서로 설명합니다. 이 챕터의 비권장 코드는 **컴파일도 되고 결과도 맞지만 쓰기 어려워진 코드**입니다. 예제는 모두 경매 하나를 이어서 씁니다. 입찰 기록 `"입찰자,금액"`을 한 줄씩 읽어 최고 입찰을 기억하고(01, 04), 끝난 경매로 낙찰 알림을 만들고(02), 출품 목록을 응찰자 화면 여러 개가 함께 봅니다(03).

### 2.1 판단의 순서

| 단계 | 할 일 | 쓰는 것 | 절 | 예제 |
| --- | --- | --- | --- | --- |
| ① 쓴다 | 데이터를 소유하는 단순한 설계로 먼저 씁니다 | `String`, `Vec<T>`, `clone()` | 2.2 | 01 |
| ② 센다 | 그 설계의 복사가 어디서 몇 번, 한 번에 얼마인지 셉니다 | 코드에 보이는 복사 자리, 복제 횟수와 바이트 | 2.3 | 02 |
| ③ 잰다 | 센 값이 문제가 될 만한 곳만 경과 시간을 잽니다 | 릴리스 빌드, `Instant`, `black_box` | 2.5 | 04 |
| ④ 바꾼다 | 측정이 가리키는 곳만 바꿉니다 | 큰 공유 데이터는 `Rc`/`Arc`, 뜨거운 경로는 빌려서 훑고 보관할 때만 복사 | 2.4·2.5 | 03·04 |

순서가 중요한 이유는 바꾸는 비용이 방향에 따라 다르기 때문입니다. 소유하는 타입의 안쪽을 나중에 빌리도록 고치는 일은 그 타입 안에서 끝납니다(2.5절에서는 `Auction`에 메서드 하나를 더할 뿐입니다). 반대로 빌린 타입을 소유하는 타입으로 고치려면, 라이프타임 매개변수가 번져 간 모든 타입과 함수의 시그니처를 함께 고쳐야 합니다. [ch14](../ch14-lifetimes/README.md) 2.8절이 "확신이 없으면 소유하는 판으로 시작한다"고 한 것도 이 때문입니다.

### 2.2 지침 1: 상태로 보관하는 타입은 데이터를 소유한다

참조를 담을지 소유할지의 일반적인 모형은 ch14 2.8절에서 자막 예제로 다뤘습니다. 이 절은 입력을 계속 받아들이며 **상태를 쌓는 타입**에서 복사를 아낀 대가가 무엇인지 봅니다.

**문제 상황.** 경매 입찰 기록을 파일이나 소켓에서 한 줄씩 읽어 최고 입찰자를 기억합니다. 입력은 얼마나 길지 모릅니다.

**비권장 코드.** 입찰자 이름을 입력 줄에서 빌려 둡니다. 이름을 하나도 복사하지 않습니다.

```rust
#[derive(Clone, Copy)]
struct BidView<'a> { bidder: &'a str, amount: u32 }

struct AuctionView<'a> { best: Option<BidView<'a>>, bids: usize }

impl<'a> AuctionView<'a> {
    fn offer(&mut self, line: &'a str) { /* 최고 입찰이 바뀌면 line의 일부를 보관 */ }
}
```

이 타입은 컴파일되고 결과도 맞습니다. 문제는 부르는 쪽에 있습니다. 경매가 이름을 빌려 두는 동안에는 그 줄이 살아 있어야 하므로, 부르는 쪽이 하던 일들이 막힙니다. 표의 에러는 모두 같은 모양의 코드를 1.100.0에서 컴파일해 확인했습니다.

| 부르는 쪽이 하려는 일 | 빌린 판 `AuctionView<'a>` | 소유한 판 `Auction` |
| --- | --- | --- |
| 줄 버퍼 하나를 다시 쓰며 읽기 | E0502 (4.1절) | 됨 (`run_auction`) |
| 줄마다 새 `String`으로 읽기 | E0597 (4.2절) | 됨 |
| 입력을 읽어 경매 결과를 돌려주는 함수 | E0515 (지역 `String`을 빌린 값을 돌려줌) | 됨 |
| 경매를 다른 스레드로 넘기기 | E0597 (``argument requires that `text` is borrowed for `'static` ``) | 됨 |
| 여러 경매의 결과를 모아 두기 | 입력 문자열을 모두 따로 보관해야 함 | 됨 |

남는 방법은 입력 전체를 `String` 하나에 읽어 두고, 그 `String`이 경매보다 오래 살게 하는 것뿐입니다. [`01_state_owns_data.rs`](examples/01_state_owns_data.rs)의 1번 구역이 그렇게 합니다. 결과를 비교해 보면 복사가 없다는 것이 메모리를 덜 쓴다는 뜻도 아닙니다.

```text
1. 빌린 판: 복사는 없지만, 입력 전체를 경매보다 오래 살려 둬야 합니다
    복사한 이름 0번, 살려 둔 입력 6줄 83바이트
2. 소유한 판: 이름을 복사하고, 줄 버퍼 하나를 다시 쓰며 읽습니다
    복사한 이름 6번 36바이트, 다시 쓴 줄 버퍼 1개
```

빌린 판은 복사를 하지 않은 대신 입력 83바이트를 경매가 끝날 때까지 붙잡습니다. 소유한 판은 이름 36바이트를 복사하고 읽은 줄은 바로 버리므로, 끝에 남는 것은 줄 버퍼 하나와 최고 입찰자의 이름뿐입니다. 입력이 수백만 줄이라면 빌린 판은 그 전부를 메모리에 두어야 합니다.

**권장 코드.** 이름을 복사해 소유합니다. 라이프타임 매개변수가 사라집니다.

```rust
struct Bid { bidder: String, amount: u32 }
struct Auction { best: Option<Bid>, bids: usize } // 라이프타임 없음

fn run_auction(mut input: impl BufRead) -> io::Result<Auction> {
    let mut auction = Auction::default();
    let mut line = String::new();
    while input.read_line(&mut line)? > 0 {
        if let Some(bid) = Bid::parse(&line) { auction.offer(bid); } // Bid::parse가 이름을 복사
        line.clear();
    }
    Ok(auction)
}
```

예제 01의 3번 구역은 빌린 판이 하지 못했던 일을 모두 합니다. 경매마다 `run_auction`이 결과를 돌려주고, 결과를 `Vec<Auction>`에 모으고, 그 목록을 정산 스레드로 옮깁니다. `Auction`은 빌린 것을 품지 않으므로 `thread::spawn`의 `'static` 바운드를 만족합니다(ch14 2.7절). 대가는 줄마다 이름 한 번의 복사입니다. 그 복사가 얼마인지는 다음 절에서 세고, 정말 문제인지는 2.5절에서 잽니다.

한 가지 주의할 점이 있습니다. 스레드로 넘기는 클로저가 `move || auction.bids`처럼 빌린 것이 없는 필드만 쓰면 빌린 판으로도 컴파일됩니다. 2021 에디션부터 클로저는 쓰는 필드만 캡처하기 때문입니다([Part 2 ch3](../../part2-editions/ch3-rust-2021/README.md) 2.5절의 분리 캡처). 경매 전체나 이름을 넘기려 하면 그때 E0597이 납니다.

**지침을 따르지 않아도 되는 경우.**

- **잠깐 처리하고 버리는 값.** 줄 하나를 나눠 검사하고 그 자리에서 결과를 쓰는 일에는 빌린 뷰가 가장 알맞습니다. 두 판이 함께 쓰는 `split_bid(line) -> Option<(&str, u32)>`가 그런 함수이고, 표준 라이브러리의 `str::lines()`와 `split_once`도 원문을 빌린 뷰를 돌려줍니다.
- **입력이 이미 통째로 메모리에 있고, 상태가 입력보다 오래 살 일이 없을 때.** 한 함수 안에서 파일 전체를 읽어 분석하고 결과만 내보낸다면 빌린 판의 제약이 드러나지 않습니다(ch14 2.8절의 판단 기준표).
- **측정이 복사를 문제로 가리켰을 때.** 그때도 보관하는 타입을 빌린 판으로 바꾸기보다, 받는 곳만 빌리게 바꿉니다(2.5절).

### 2.3 지침 2: 보이는 복사를 지우려 하지 말고, 먼저 센다

**문제 상황.** 경매가 끝나면 낙찰 알림(물품, 낙찰자, 금액)을 만들어 발송 큐에 넣고, 경매 기록은 정리합니다. 알림을 만드는 코드에 `clone()`이 줄줄이 보여서 지우고 싶어집니다.

**비권장 코드.** 복제를 피하려고 알림이 판매 기록을 빌립니다.

```rust
struct NoticeView<'a> { item: &'a str, winner: &'a str, amount: u32 }

fn notices_view(sales: &[Sale]) -> Vec<NoticeView<'_>> // 결과가 sales에 묶임
```

알림을 다 보낼 때까지 판매 기록을 버릴 수 없습니다. 알림이 남아 있는데 `drop(sales)`를 부르면 ``error[E0505]: cannot move out of `sales` because it is borrowed``이고, 큐를 발송 스레드로 넘기려 하면 2.2절의 표처럼 E0597(``requires that `sales` is borrowed for `'static` ``)입니다. 그렇게 해서 아낀 것이 얼마인지는 세어 봐야 압니다.

**권장 코드.** 그냥 복제하고, 복제를 셉니다.

```rust
fn notices(sales: &[Sale]) -> Vec<Notice> {
    sales.iter()
        .map(|s| Notice { item: s.item.clone(), winner: s.winner.clone(), amount: s.amount })
        .collect()
}
```

[`02_count_the_copies.rs`](examples/02_count_the_copies.rs)의 1번 구역에서 알림 3건에 `clone()`은 6번, 복사한 글자는 42바이트입니다. 판매 기록을 정리한 뒤에도 알림은 그대로 보낼 수 있습니다. 알림을 실제로 보내는 일(메일, 네트워크)에 비하면 42바이트의 복사는 비교할 거리가 되지 않습니다. 셀 수 있으면 두려워할 이유가 없습니다.

**세는 방법.** 복사의 비용은 "몇 번 × 한 번에 얼마"입니다.

- **몇 번**: 코드에 보이는 복사 자리(`clone()`, `to_string()`, `to_owned()`, `to_vec()`, `format!`, `Box::new`, 소유한 컬렉션으로의 `collect()`)를 찾고, 그 자리를 감싼 반복문의 횟수를 곱합니다. 확인하고 싶으면 예제 01의 `copy_name`처럼 복사하는 함수에서 횟수와 바이트를 세거나, 예제 03의 `Catalog`처럼 `Clone`을 직접 구현해 셉니다.
- **한 번에 얼마**: 타입이 정합니다. 예제 02의 2번 구역이 `clone()` 뒤에 가리키는 곳이 같은지(`ptr::eq`, `Rc::ptr_eq`)로 확인합니다.

| 타입 | `clone()` 한 번이 하는 일 | 예제 02의 출력 |
| --- | --- | --- |
| `u32` 같은 `Copy` 타입 | 비트 복사 | `u32: 비트 복사 4바이트` |
| `&str`, `&T` | 참조만 비트 복사. 가리키는 데이터는 그대로 | `글자가 같은 곳 true` |
| `String`, `Box<str>`, `Vec<T>` | 새 버퍼 할당 + 내용 전체 복사 | `새 버퍼에 16바이트 복사, 같은 곳 false` |
| `Vec<String>` | 목록과 원소마다 새 버퍼(깊은 복제) | `새 버퍼 4개(목록 1 + 원소 3)` |
| `Rc<T>` | 카운트 1 증가. 새 버퍼 없음 | `같은 곳 true, 카운트 1 → 2` |
| `Arc<T>` | 카운트를 원자적으로 1 증가 | `같은 곳 true, 카운트 1 → 2` |

`Rc`와 `Arc`의 싼 복제는 `Rc::clone(&x)`로 써 두면 비싼 `clone()`과 눈으로 구별됩니다(Part 0 ch14 2.7절의 관례). 이 표기를 강제하는 clippy 린트 `clone_on_ref_ptr`는 restriction 그룹이라 기본으로 꺼져 있고, 켜면 `a: Rc<str>`의 `a.clone()`에 ``using `.clone()` on a ref-counted pointer``를 경고하며 `std::rc::Rc::<str>::clone(&a)`를 제안합니다(직접 켜서 확인). 반대로 쓸데없는 복제를 잡는 `redundant_clone`도 기본으로 꺼져 있습니다. clippy는 복제를 세어 주지 않으므로 세는 일은 사람의 몫입니다.

`Copy` 타입은 `clone()`도 쓰지 않고 조용히 복사됩니다. 그래서 비트 복사가 유효하고 빠를 때만 `Copy`를 붙이고, 반대로 필드 없는 열거형처럼 작고 값처럼 행동하는 타입에는 붙여 쓰기 편하게 합니다. 기준은 [ch10](../ch10-standard-traits/README.md) 2.3절에서 다뤘습니다.

**지침을 따르지 않아도 되는 경우.**

- **횟수 × 크기가 클 때.** 큰 데이터를 여러 곳에 통째로 복제하고 있다면 세는 단계에서 바로 드러납니다. 2.4절의 공유 소유로 갑니다.
- **작은 복사라도 횟수가 입력에 비례해 아주 많을 때.** 줄마다 하는 복사처럼 뜨거운 경로에 있다면 재 볼 만합니다(2.5절). 횟수가 입력 크기의 제곱으로 느는 복사(반복문 안에서 목록 전체를 복제하는 코드)는 재지 않아도 세는 것만으로 고칠 이유가 됩니다.
- **할당 자체를 피해야 하는 환경.** 책은 할당을 피하는 코드가 `no_std`(표준 라이브러리 없이 도는 환경) 지원을 쉽게 하지만, 힙이 있는 `alloc` 환경을 목표로 하는 편이 쓰기 편함과 균형이 맞을 수 있다고 봅니다. [`ch33-no-std`](../ch33-no-std/README.md)에서 다룹니다.

### 2.4 지침 3: 여러 곳이 함께 갖는 큰 데이터는 라이프타임 대신 공유 소유로 나눈다

[ch8](../ch8-references-pointers/README.md) 2.6절은 같은 사진을 두 앨범에 넣을 때 복제판과 `Rc`판을 비교했습니다. 이 절은 `Rc`를 **빌린 판**, 즉 복사를 아끼려고 라이프타임을 들인 설계와 비교합니다.

**문제 상황.** 경매장의 출품 목록(카탈로그)은 물품 40개에 설명이 길어 한 벌이 51791바이트입니다. 응찰자 20명의 화면이 저마다 이 카탈로그를 보며 관심 물품을 고릅니다.

**비권장 코드 1: 빌린 판.** 복사가 없도록 화면이 카탈로그를 빌립니다.

```rust
struct ScreenView<'a> { bidder: String, catalog: &'a Catalog, watching: Vec<usize> }
struct HallView<'a> { screens: Vec<ScreenView<'a>> } // 'a가 번짐

fn open_hall_view(catalog: &Catalog) -> HallView<'_>
```

`'a`가 화면에서 홀로, 홀을 담는 타입으로 번집니다. 홀을 여는 함수는 카탈로그를 직접 불러올 수 없습니다. 지역 값을 빌린 홀은 돌려줄 수 없으므로(E0515), 부르는 쪽이 카탈로그를 먼저 불러 홀보다 오래 들고 있어야 합니다. 홀을 다른 스레드로 넘기는 것도 2.2절과 같은 이유로 막힙니다.

**비권장 코드 2: 복제판.** 화면마다 카탈로그를 복제하면 라이프타임은 사라지지만, [`03_share_instead_of_borrow.rs`](examples/03_share_instead_of_borrow.rs)의 2번 구역에서 복제 20번, 1035820바이트를 옮겨 적습니다. 2.3절의 방법으로 세면 바로 드러나는 크기입니다.

**권장 코드: `Rc`판.**

```rust
struct Screen { bidder: String, catalog: Rc<Catalog>, watching: Vec<usize> }
struct Hall { catalog: Rc<Catalog>, screens: Vec<Screen> } // 라이프타임 없음

fn open_hall() -> Hall // 카탈로그를 안에서 불러와 홀째로 돌려줌
```

3번 구역에서 카탈로그 복제는 0번이고, 모든 화면이 같은 카탈로그를 가리키며(`Rc::ptr_eq`), 카운트는 21(홀 1 + 화면 20)입니다. 빌린 판처럼 복사가 없으면서, 복제판처럼 라이프타임도 없습니다. 홀을 닫으면 카운트가 1로 돌아오고, 마지막 소유자는 `Rc::unwrap_or_clone`으로 카탈로그를 복사 없이 꺼냅니다. 이 함수는 `Rc`를 혼자 가지고 있으면 안의 값을 그대로 꺼내고, 다른 소유자가 남아 있을 때만 복제합니다.

| 같은 카탈로그를 나누는 세 판 | 복사 | 라이프타임 매개변수 | 홀을 여는 함수가 카탈로그를 불러와 돌려주기 |
| --- | --- | --- | --- |
| 빌린 판 | 0바이트 | 화면, 홀, 홀을 담는 모든 타입 | 불가(E0515). 부르는 쪽이 따로 보관 |
| 복제판 | 1035820바이트 | 없음 | 됨 |
| `Rc`판 | 0바이트, 카운트만 증가 | 없음 | 됨 |

책은 스마트 포인터를 쓰는 것이 마지막 수단이나 패배가 아니며, 라이프타임이 서로 얽힌 설계보다 더 단순하고 유지하기 쉬운 설계일 수 있다고 강조합니다. 위 표가 그 이유입니다.

**고칠 수 있는 데이터라면.** 경매 중에 출품이 취소되는 것처럼 함께 보는 데이터가 바뀐다면, 복제판은 사본 20개를 모두 찾아 고쳐야 하고 하나라도 빠뜨리면 화면끼리 어긋납니다. `Rc`는 안의 값을 고칠 수 없으므로 내부 가변성과 함께 씁니다. 한 스레드에서는 `Rc<RefCell<T>>`, 스레드를 넘으면 `Arc<Mutex<T>>`입니다. 사본이 어긋나는 모습과 `Rc<RefCell<T>>`판의 비용(실행 중 대여 실패)은 [ch15](../ch15-borrow-checker/README.md) 2.7~2.8절에서, 고칠 칸에만 내부 가변성을 두는 방법은 ch8 2.7절에서 다뤘습니다(연습 4). `Rc`는 `Send`가 아니므로 스레드를 넘는 공유는 `Arc`로 합니다(ch8 2.6절). `Mutex`와 잠금은 [`ch17-shared-state-parallelism`](../ch17-shared-state-parallelism/README.md)에서 다룹니다.

**지침을 따르지 않아도 되는 경우.**

- **작은 데이터.** 2.3절처럼 복제가 가장 단순합니다. `Rc`는 할당마다 카운트 두 개를 더 두고, 안의 값을 고칠 수 없게 만듭니다.
- **소유자가 분명하고 다른 쪽은 그보다 짧게 쓰기만 할 때.** 함수 매개변수나 스코프 스레드처럼 빌려 쓰고 바로 끝나는 곳에는 참조가 맞습니다(ch14 2.8절, ch8 2.6절).
- **각자 따로 고쳐야 하는 데이터.** 공유가 아니라 복제가 맞는 모델입니다.

### 2.5 지침 4: 바꾸기 전에 재고, 측정이 가리키는 곳만 바꾼다

**문제 상황.** 경매 서비스가 커져서 입찰 기록 10만 줄을 처리하는 일이 잦아졌습니다. 2.3절의 방법으로 세어 보니 2.2절의 소유한 판은 줄마다 이름을 복사하므로 10만 번 복사합니다. 이것이 정말 문제인지 판단해야 합니다.

**비권장 코드.** 재지 않고 2.2절의 빌린 판으로 갈아엎는 섣부른 최적화입니다. 2.2절의 표에 있는 대가를 모든 부르는 쪽이 치릅니다. 재더라도 디버그 빌드로 재거나, 한 번만 재거나, 결과가 같은지 확인하지 않고 재면 판단을 그르칩니다.

**측정하는 방법(책에 없는 지침).** [`04_measure_then_change.rs`](examples/04_measure_then_change.rs)는 다음을 지킵니다.

1. **결과부터 맞춥니다.** 세 판의 결과(최고 입찰과 입찰 수)가 같은지 먼저 출력합니다. 빠르지만 틀린 판은 비교할 의미가 없습니다. 복사 횟수도 이때 함께 셉니다.
2. **릴리스 빌드로 잽니다.** 디버그 빌드는 최적화를 끈 빌드라 실제 비용을 대표하지 않습니다(아래의 측정 결과).
3. **여러 번 재서 가장 짧은 값을 봅니다.** 다른 프로그램이 끼어든 측정은 길어지기만 하므로, 가장 짧은 값이 그 코드의 비용에 가장 가깝습니다. 그래도 값은 실행마다 다릅니다.
4. **`std::hint::black_box`로 입력과 결과를 감쌉니다.** 컴파일러가 입력을 안다고 가정하거나, 쓰이지 않는 결과라며 계산을 지우는 최적화를 막습니다. 문서는 이것이 "최선의 노력"일 뿐 보장은 아니라고 적습니다.

```rust
fn fastest<T>(mut work: impl FnMut() -> T) -> Duration {
    (0..RUNS)
        .map(|_| {
            let start = Instant::now();
            black_box(work());
            start.elapsed()
        })
        .min()
        .unwrap_or_default()
}

report("소유한 판", fastest(|| run_owned(black_box(&text))));
```

**측정 결과.** 이 환경(macOS aarch64, rustc 1.100.0)에서 예제 04를 디버그 빌드로 1번, 릴리스 빌드로 15번 실행한 결과입니다. 시간은 실행마다 다릅니다.

| 판 | 이름 복사 | 디버그 빌드 | 릴리스 빌드(15번의 가운데 값) | 릴리스 빌드(15번의 범위) |
| --- | --- | --- | --- | --- |
| 소유한 판: 줄마다 복사 | 100000번 | 38.22ms | 3.04ms | 2.84~4.19ms |
| 빌린 판: 복사 없음 | 0번 | 33.80ms | 1.76ms | 1.62~2.22ms |
| 경계판: 보관할 때만 복사(아래) | 15번 | 33.91ms | 1.74ms | 1.65~2.09ms |

릴리스 빌드에서 소유한 판은 같은 실행의 빌린 판보다 1.03~1.97ms(가운데 값 1.29ms) 더 걸렸습니다. 10만 줄이므로 줄당 13ns 안팎이고, 소유한 판 시간의 36~47%가 이름 복사입니다. 디버그 빌드에서는 두 판의 차이가 전체의 11% 남짓으로 보입니다. 최적화가 꺼져 다른 일이 모두 느려진 탓입니다. 디버그 빌드로 쟀다면 "복사는 별것 아니다"라는 틀린 결론에 이르렀을 것입니다. 반대 방향으로 틀리는 경우도 있습니다. Part 0 ch13 2.15절에서는 디버그 빌드에서 반복자가 반복문보다 눈에 띄게 느렸지만 릴리스 빌드에서는 비슷했습니다.

이 숫자로 판단합니다. 입찰이 네트워크로 한 건씩 들어온다면 줄당 십여 ns는 그 비용에 묻힙니다. 소유한 판을 그대로 둡니다. 반대로 기록 파일을 한꺼번에 분석하는 일이 서비스의 대부분이라면 줄마다 하는 복사가 시간의 40% 안팎이므로 바꿀 이유가 있습니다.

**권장 코드: 측정이 가리킨 곳만 바꿉니다.** 측정이 가리킨 것은 "줄마다 하는 복사"이지 "`Auction`이 이름을 소유하는 것"이 아닙니다. 그래서 `Auction`에 줄을 빌려 받는 메서드 하나를 더하고, 보관하는 순간에만 복사합니다.

```rust
impl Auction {
    /// 줄을 빌려 받고, 최고 입찰이 바뀔 때만 이름을 복사합니다.
    fn offer_line(&mut self, line: &str) -> bool {
        let Some((bidder, amount)) = split_bid(line) else { return false };
        self.bids += 1;
        if self.best.as_ref().is_none_or(|b| amount > b.amount) {
            self.best = Some(Bid { bidder: bidder.to_string(), amount }); // 보관하는 순간에만
            return true;
        }
        false
    }
}
```

이 경계판은 이름을 15번(최고 입찰이 바뀐 횟수)만 복사하고, 시간은 빌린 판과 실행마다 앞서거니 뒤서거니 할 만큼 비슷합니다(15번 중 10번은 경계판이, 5번은 빌린 판이 0.13ms 이하의 차이로 빨랐습니다). 그러면서 `Auction` 타입은 그대로라 라이프타임 매개변수가 없고, 2.2절의 표에서 소유한 판이 할 수 있던 일을 모두 그대로 할 수 있습니다. "받는 쪽은 빌리고, 보관하는 쪽은 소유한다"는 경계는 ch8 2.2절(매개변수는 가리키는 대상으로)과 ch14 2.8절(오래 보관하는 타입에는 소유)이 만나는 곳입니다. 대개는 빌리고 가끔만 소유한 값을 돌려줘야 하는 함수라면 `Cow`가 같은 일을 합니다([Part 1 ch6](../../part1-standard-lib/ch6-core-traits/README.md) 2.7절, ch15 2.4절. 연습 3).

**측정의 함정.**

- **디버그 빌드.** 위의 표처럼 비율이 달라집니다.
- **실행마다 다른 값.** 같은 릴리스 빌드를 15번 실행했을 때 소유한 판은 2.84~4.19ms였습니다. 4.19ms와 3.73ms가 나온 두 실행에서는 같은 실행의 다른 두 판도 함께 길어졌습니다(빌린 판 2.22ms, 2.07ms). 각 판을 여러 번 재서 가장 짧은 값을 골라도 컴퓨터 전체가 바쁘면 모두 느려지므로, 비교할 판들은 같은 실행 안에서 함께 재고 여러 번 실행해 봅니다. 빌린 판과 경계판처럼 차이가 이 흔들림보다 작은 두 판은 "어느 쪽이 빠르다"고 말할 수 없습니다. 예제가 순위를 출력하지 않는 이유입니다.
- **지워진 계산.** 결과를 쓰지 않는 계산은 최적화로 사라질 수 있습니다. Part 0 ch13에서는 `black_box`를 빠뜨린 측정이 `0ns`로 나왔고, Part 1 ch10 2.12절에서는 입력을 감싸도 반복문이 다른 계산으로 바뀌어 40ns 안팎이 나왔습니다. 이 챕터를 쓰면서 줄마다 `split_bid`를 부르고 결과를 버리는 반복문을 `black_box` 없이 재 보았을 때는 빌린 판과 비슷한 시간이 나와 지워지지 않았지만, 그것은 문자열을 나누고 숫자를 파싱하는 이 코드의 사정일 뿐 보장이 아닙니다. 줄당 시간이 1ns보다 작게 나오는 것처럼 믿기 어려운 값이 나오면 먼저 무엇을 재고 있는지 의심합니다.

통계로 측정값을 다루는 벤치마크 도구(`criterion`)와 벤치마크를 테스트처럼 관리하는 방법은 [`ch30-beyond-unit-tests`](../ch30-beyond-unit-tests/README.md)에서, 릴리스 빌드의 최적화 수준 같은 프로필 설정은 [Part 3 ch6](../../part3-cargo/ch6-profiles-build-performance/README.md)에서 다룹니다.

**지침을 따르지 않아도 되는 경우.** 2.3절의 제곱으로 느는 복사처럼 세는 것만으로 분명한 낭비는 재지 않고 고칩니다. 처음부터 성능 요구가 정해진 코드(예: 프레임마다 정해진 시간 안에 끝나야 하는 코드)라면 설계 단계에서부터 측정을 함께 둡니다.

### 2.6 책과 달라진 점

책은 2018 에디션, rustc 1.70을 기준으로 합니다. rustc 1.100.0에서 확인한 차이는 다음과 같습니다.

- **책의 두 에러 상황은 그대로입니다.** 빌린 값을 보관하는 상태 타입에 줄마다 새 버퍼를 넘기면 E0597, 버퍼 하나를 다시 쓰면 E0502라는 책의 설명은 1.100.0에서도 같습니다(4.1·4.2절). 구조체 필드에 보관하는 모양에서는 도움말이 붙지 않습니다. 빌린 값을 **컬렉션**에 모으는 모양이라면 ``note: `names` is a collection that stores borrowed references``와 ``help: buffer reuse with borrowed references requires unsafe code or restructuring``이 붙습니다(같은 모양의 코드로 확인, ch14 4.2절). 여기서 말하는 구조 변경(restructuring)이 이 챕터의 소유한 판입니다.
- **`Rc::unwrap_or_clone`과 `Arc::unwrap_or_clone`(1.76.0).** 책 이후에 안정화되었습니다(로컬 문서의 안정화 버전 표시로 확인). 공유가 끝난 값을 복사 없이 소유로 되돌리는 데 씁니다(2.4절).
- **분리 캡처.** 책의 2018 에디션과 달리 2021 에디션부터는 클로저가 쓰는 필드만 캡처하므로, 빌린 판의 상태에서 빌리지 않은 필드만 스레드로 넘기는 클로저는 컴파일됩니다(2.2절).
- **책에 없는 지침.** 다음은 책의 Item 20이 직접 권하지 않는 내용입니다(2026-11-19에 온라인판에서 확인). 책은 빌린 타입이 상태 보관에 맞지 않는다는 것, 복사가 눈에 보인다고 없애지 말 것, 성능이 실제 문제이고 벤치마크가 의미 있는 이득을 보일 때만 최적화할 것(Item 30으로 넘김), `Copy`와 `no_std`에 관한 언급, 스마트 포인터가 마지막 수단이 아니라는 것까지 다룹니다.
  - 2.1절의 "판단의 순서" 표와 그중 ② 세기 단계, 2.3절의 세는 방법과 타입별 `clone()` 한 번의 값 표: 책은 복사가 코드에 보인다는 데까지 말합니다. 표의 내용은 예제 02의 실행 결과(가리키는 곳 비교, 카운트)가 근거입니다.
  - 2.2절 표의 "함수에서 돌려받기, 스레드로 넘기기, 모아 두기": 책이 보여 주는 것은 줄 단위로 읽는 두 상황(E0597, E0502)입니다. 나머지 칸은 같은 모양의 코드를 컴파일한 결과가 근거입니다.
  - 2.3절의 `Rc::clone(&x)` 표기와 `clone_on_ref_ptr`: Part 0 ch14의 관례와, 린트를 직접 켜서 본 경고가 근거입니다. 같은 절의 "제곱으로 느는 복사는 재지 않고 고친다"는 이 챕터의 판단입니다.
  - 2.5절의 측정 방법(릴리스 빌드, 결과 확인, 여러 번 재서 가장 짧은 값, `black_box`)과 경계판: `black_box` 문서, Part 0 ch13·Part 1 ch10의 측정 경험, 예제 04의 실행 결과가 근거입니다. 경계판의 "받는 쪽은 빌리고, 보관하는 쪽은 소유한다"는 ch8 2.2절과 ch14 2.8절의 지침을 이은 것입니다.

### 2.7 기억할 것

- 먼저 데이터를 소유하는 단순한 설계로 씁니다. 상태로 보관하는 타입에 빌린 데이터를 담으면 라이프타임이 번지고, 부르는 쪽은 버퍼 재사용·반환·스레드로 넘기기·모아 두기를 잃습니다.
- `clone()`이 보인다고 비싼 것은 아닙니다. "몇 번 × 한 번에 얼마"로 셉니다. `Rc::clone`은 카운트 증가, `String::clone`은 할당과 복사입니다.
- 큰 데이터를 여러 곳이 함께 가져야 하면 라이프타임 그물이나 통째 복제 대신 `Rc`/`Arc`로 나눠 가집니다. 스마트 포인터는 마지막 수단이 아닙니다.
- 바꾸기 전에 잽니다. 결과가 같은지 먼저 확인하고, 릴리스 빌드에서, `black_box`로 감싸, 여러 번 잽니다.
- 측정이 가리키는 곳만 바꿉니다. 받을 때는 빌리고 보관할 때만 복사하면, 보관하는 타입은 소유한 채로 남습니다.

### 4.1 빌린 값을 보관한 채 줄 버퍼를 다시 씀 — E0502

파일: [`compile_fail/e0502_reuse_line_buffer.rs`](compile_fail/e0502_reuse_line_buffer.rs)

```text
error[E0502]: cannot borrow `line` as mutable because it is also borrowed as immutable
  --> compile_fail/e0502_reuse_line_buffer.rs:52:27
   |
52 |     while input.read_line(&mut line).unwrap_or(0) > 0 { // E0502: 다음 줄을 읽으려고 버퍼를 빌림
   |                           ^^^^^^^^^ mutable borrow occurs here
53 |         auction.offer(&line); // 경매가 버퍼를 빌려 이름을 보관
   |         -------       ----- immutable borrow occurs here
   |         |
   |         immutable borrow later used here

error[E0502]: cannot borrow `line` as mutable because it is also borrowed as immutable
  --> compile_fail/e0502_reuse_line_buffer.rs:54:9
   |
53 |         auction.offer(&line); // 경매가 버퍼를 빌려 이름을 보관
   |         -------       ----- immutable borrow occurs here
   |         |
   |         immutable borrow later used here
54 |         line.clear(); // E0502: 빌려 준 버퍼를 비움
   |         ^^^^^^^^^^^^ mutable borrow occurs here
```

- **읽는 법**: 두 에러 모두 세 표시가 같은 줄(53행)에 몰려 있습니다. `&line`으로 빌린 곳과 "그 뒤에 쓰는 곳"인 `auction.offer`가 같은 줄인 것은, 뒤에 쓰는 것이 **다음 반복**의 `auction.offer`이기 때문입니다. 경매가 앞 반복에서 빌린 이름을 들고 있는 채로 다시 쓰이므로, 대여가 반복을 건너 이어집니다. 버퍼를 다시 쓰는 두 지점(`read_line`, `clear`)에서 각각 에러가 납니다.
- **원인**: 경매가 줄 버퍼의 일부를 보관하는데, 다음 줄을 읽거나 비우면 보관한 이름이 바뀌거나 사라집니다(2.2절).
- **해결**: 경매가 이름을 소유하게 합니다(예제 01의 `Auction`과 `run_auction`). 보관하는 순간에만 복사하는 경계판(예제 04의 `offer_line`)이면 복사도 최고 입찰이 바뀔 때뿐입니다. 입력 전체를 `String` 하나에 읽어 경매보다 오래 살리는 방법(예제 01의 1번 구역)도 컴파일되지만, 버퍼를 다시 쓰는 장점을 잃고 입력 전체를 메모리에 둡니다.

### 4.2 빌린 값을 보관한 채 줄마다 새 버퍼를 만듦 — E0597

파일: [`compile_fail/e0597_new_line_each_round.rs`](compile_fail/e0597_new_line_each_round.rs)

```text
error[E0597]: `line` does not live long enough
  --> compile_fail/e0597_new_line_each_round.rs:55:23
   |
51 |         let mut line = String::new(); // 줄마다 새 버퍼
   |             -------- binding `line` declared here
...
55 |         auction.offer(&line); // E0597: 이번 반복에서만 사는 줄을 경매가 빌림
   |         -------       ^^^^^ borrowed value does not live long enough
   |         |
   |         borrow later used here
56 |     } // line이 여기서 drop됩니다
   |     - `line` dropped here while still borrowed
```

- **읽는 법**: 4.1절에서 막혀 버퍼를 다시 쓰지 않게 바꿨더니, 이번에는 반복이 끝나는 56행에서 버퍼가 drop됩니다. "그 뒤에 쓰는 곳"은 역시 다음 반복의 `auction.offer`입니다. 4.1절과 4.2절을 합치면, 빌린 판으로는 버퍼를 다시 써도 새로 만들어도 줄 단위로 읽을 수 없습니다.
- **원인**: 경매가 반복 한 번만 사는 값을 빌려 반복 밖까지 들고 갑니다. 필드에 보관하는 이 모양에는 도움말이 붙지 않습니다(2.6절).
- **해결**: 4.1절과 같습니다. 경매가 이름을 소유하게 합니다.

## 5. 연습 문제

### 연습 1. 체인과 반복문 재기

[ch9](../ch9-iterator-transforms/README.md)의 [`01_loop_to_chain.rs`](../ch9-iterator-transforms/examples/01_loop_to_chain.rs)에는 인덱스 반복문판(`credited_v0_index`)부터 체인판(`credited_v4_chain`)까지 같은 일을 하는 함수가 다섯 개 있습니다. 예제 04의 `fastest`와 `report`를 가져와 기록 100만 건에서 다섯 판의 시간을 디버그 빌드와 릴리스 빌드로 재 보세요.

<details>
<summary>힌트</summary>

먼저 `session`으로 큰 기록을 만들고(빈 기록이 섞이도록 `Option`을 번갈아 넣습니다), 다섯 판의 결과가 같은지 확인한 뒤에 잽니다. 이 함수들은 `LAST_DAY`(14일)를 넘는 날에서 멈추므로, 날짜를 1, 2, 3, …으로 매기면 14건만 보고 끝나 재는 의미가 없습니다. 날짜를 `1 + (i * 14 / n) as u32`처럼 1~14 안에서 날짜순으로 나눠 100만 건을 모두 보게 합니다. 입력이 재려는 일을 실제로 시키는지 확인하는 것도 측정의 일부입니다. 입력과 결과는 `black_box`로 감쌉니다. Part 0 ch13 2.15절이 비슷한 비교에서 본 경향(릴리스 빌드에서는 두 판이 비슷하고, 디버그 빌드에서는 일부 작업에서 반복자 판이 눈에 띄게 느림)이 이 코드에서도 나오는지 확인하고, 차이가 실행마다의 흔들림보다 큰지도 봅니다. 결과가 그렇게 나오지 않았다면 그 결과를 믿습니다. 측정은 짐작을 확인하려는 것이 아니라 짐작을 대신하려는 것입니다.

</details>

### 연습 2. 제네릭판과 `dyn`판의 비용 재기

[ch12](../ch12-generics-vs-trait-objects/README.md) 2.2절은 제네릭판과 `dyn`판의 호출 비용 차이를, 2.3절은 얇은 제네릭 껍데기가 줄이는 코드 크기를 측정 없이 남겨 두었습니다. (가) `due_note`와 `due_note_dyn`을 같은 자료 목록에 여러 번 불러 시간을 재고, (나) `shelf_label_fat`만 쓰는 프로그램과 `shelf_label`만 쓰는 프로그램을 따로 만들어 릴리스 빌드의 실행 파일 크기를 비교해 보세요.

<details>
<summary>힌트</summary>

(가) `due_note`는 `format!`으로 문자열을 만들므로 호출 방식의 차이가 할당 비용에 묻힐 수 있습니다. 무엇을 재고 있는지 생각해 보고, 필요하면 `loan_days()`만 더하는 함수로 바꿔 재 봅니다. (나) 실행 파일 크기는 `ls -l`로 봅니다(예: `ls -l target/release/examples/<이름>`). 릴리스 빌드에서는 함수가 인라인되어 ch12처럼 `nm`으로 함수 수를 셀 수 없으므로 파일 크기로 비교합니다. 표준 라이브러리 코드가 크기의 대부분을 차지하므로, 차이가 작게 나온다면 그것도 측정이 알려 준 사실입니다.

</details>

### 연습 3. 대개는 빌리고 가끔만 소유하기

입찰자 이름이 가끔 `"MinJun"`처럼 영문 대문자가 섞여 들어오고, 경매는 이름을 소문자로 맞춰 비교해야 한다고 합시다. 대부분의 이름은 한글이거나 이미 소문자입니다. `fn normalize(name: &str) -> Cow<'_, str>`를 만들어 예제 04의 경계판에 끼워 넣고, 입찰 10만 줄 중 새 `String`을 만든 횟수를 세어 보세요.

<details>
<summary>힌트</summary>

`name.chars().any(char::is_uppercase)`가 거짓이면 `Cow::Borrowed(name)`, 참이면 `Cow::Owned(name.to_lowercase())`를 돌려줍니다. 경계판은 최고 입찰이 바뀔 때 `normalize(bidder).into_owned()`로 보관합니다. `Borrowed`면 그때 한 번 복사하고, `Owned`면 이미 만든 `String`을 그대로 꺼냅니다. 생성기의 `NAMES`에 영문 이름을 몇 개 섞어 새 `String`을 만든 횟수가 그 이름의 등장 횟수와 같은지 확인합니다. `Cow`는 [Part 1 ch6](../../part1-standard-lib/ch6-core-traits/README.md) 2.7절과 [ch15](../ch15-borrow-checker/README.md) 2.4절에서 다뤘습니다.

</details>

<details>
<summary>힌트</summary>

</details>
