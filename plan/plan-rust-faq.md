# 부록 B: Rust FAQ 집필 계획

다른 언어를 써 온 프로그래머가 Rust를 처음 볼 때 자주 묻는 질문을 모아 답하는 **부록 B**(`appd-b/`)의 집필 계획입니다. [로드맵](../docs/roadmap.md)의 본편(Part 0~11), [부록 A](plan-effective-rust.md)와 별도인 파트이며, 챕터 작성과 검증은 `/writing-guide` 스킬의 절차(메인 세션이 쓰고 reviewer가 검증)를 그대로 따릅니다.

- 작성일: 2026-11-21
- 규모: 사전 작업 9건, 챕터 17개(질문 165개), 마무리 1회
- 선수 과정: Part 0(완료). Part 1과 부록 A는 전제하지 않고 "더 읽기"로 연결합니다.
- 상태 표기: ⬜ 대기 · 🔄 작성 중 · ✅ 완료
- 2026-11-21 확정: 사용자가 9절의 네 가지를 정했습니다. **Part 3이 끝난 뒤 사용자가 요청하면** 사전 작업부터 시작합니다. 그 전에는 이 문서 말고 아무것도 고치지 않습니다.

## 1. 개요

### 1.1 독자와 목적

독자는 C/C++, Java, C#, Go, Python, JavaScript/TypeScript 가운데 하나 이상을 실무에서 써 본 사람입니다. 이 독자는 문법보다 먼저 이런 것을 묻습니다.

1. **왜 Rust인가**: 왜 보안성이 좋다고 하는가, 왜 여러 조직이 Rust로 옮기는가, 어디까지 믿을 수 있는가
2. **무엇이 다른가**: GC, `null`, 예외, 클래스와 상속이 없다는데 그 자리를 무엇이 채우는가
3. **C/C++의 문제를 어떻게 풀었는가**: 메모리 오류, 미정의 동작, 헤더와 빌드 시스템
4. **실무에서 쓸 만한가**: 성능, 학습 비용, 생태계, 기존 코드와의 연동

부록 B는 이 네 묶음을 순서대로 다룹니다. 본편이 "무엇이 있고 어떻게 쓰는가"를, 부록 A가 "여러 방법 중 무엇을 왜 고르는가"를 다룬다면, 부록 B는 **"왜 그렇게 만들었고, 내가 쓰던 언어와 무엇이 다른가"** 를 다룹니다.

### 1.3 본편·부록 A와 다른 점

- **구성 단위가 질문입니다.** 챕터 하나가 주제 하나를 맡고, 그 안에 질문 7~12개가 있습니다. 질문에는 `Q4.2`(ch4의 두 번째 질문)처럼 번호를 붙여 다른 챕터에서 가리킵니다.
- **가르치지 않고 답합니다.** 문법과 API 사용법은 본편 챕터로 링크합니다. 질문마다 "짧은 답 → 왜 그런가 → 다른 언어에서는 → 오해와 한계" 순서로 씁니다(2.2절).
- **다른 언어와의 비교가 중심입니다.** 본편과 부록 A는 비교를 "이해에 도움이 될 때만" 쓰지만, 부록 B는 독자가 아는 언어에서 출발합니다. C/C++ 비교 코드는 실제로 컴파일해 확인합니다(2.4절).
- **언어 밖의 사실을 다룹니다.** 취약점 통계, 도입 사례, 표준화 현황은 실행해서 확인할 수 없고 시간이 지나면 낡습니다. 출처와 발행일, 확인일을 함께 적습니다(1.5절).
- **한계를 함께 답합니다.** "Rust가 막지 못하는 것"(ch3), "C++가 더 나은 점"(Q12.6), "왜 어렵다고 하는가"(ch15)를 독립된 주제로 둡니다. 홍보 문구와 출처 없는 성능 수치는 쓰지 않습니다.

### 1.5 시점에 기대는 사실

통계, 도입 사례, 표준화와 도구의 현황은 낡습니다. 다음을 지킵니다.

- 본문에 수치를 적을 때는 **누가, 언제, 무엇을 센 숫자인지**를 함께 적습니다. 예: "Microsoft가 CVE를 부여한 취약점 가운데(2019년 발표)".
- 챕터 README의 "참고 자료"에 자료마다 발행일과 확인일을 적습니다.
- 수치가 주장의 전부가 되지 않게 씁니다. 숫자가 바뀌어도 설명(왜 그런 차이가 나는가)은 남아야 합니다.
- 완료한 뒤 `SHARED.md` 2.5절(시점에 기대는 것)에 챕터와 확인일을 적습니다.

### 1.6 저작권

- F1~F5와 R1~R17의 본문을 번역하거나 발췌하지 않습니다. 교재의 코드도 옮기지 않습니다. 가져오는 것은 "어떤 질문이 나오는가"와 출처를 밝힌 사실(수치, 날짜)뿐입니다.
- 통계와 사례는 한두 문장으로 풀어 쓰고 링크합니다. 인용 부호로 옮기는 것은 꼭 필요한 한 문장 이내로 합니다.
- 설명의 흐름과 예제는 모두 새로 설계합니다.

### 2.2 README 구성

로드맵 2.4절의 여섯 항목을 유지하고 다음과 같이 씁니다.

- 제목은 `# ch4. (한국어 제목)`, 첫머리에 패키지 이름과 **이 챕터가 답하는 질문 표**(번호, 질문, 한 줄 답)를 둡니다. 급한 독자는 이 표만 읽어도 됩니다.
- **학습 목표**: "~라는 질문에 근거를 들어 답할 수 있다" 형태로 3~5개.
- **핵심 개념**: 질문 하나가 소절 하나입니다.

  ```
  ### Q4.2 변수를 함수에 넘겼더니 왜 더 쓸 수 없나요?

  **짧은 답** 2~4문장. 이 문단만 읽어도 답이 됩니다.
  **왜 그런가** 설계한 이유와 막으려는 문제. 짧은 코드 조각과 examples/ 링크.
  **다른 언어에서는** (해당할 때만) 독자가 아는 언어의 동작과 나란히. 표나 10줄 이하 조각.
  **오해와 한계** 흔한 오해, Rust가 치르는 비용, 예외.
  **더 읽기** 본편과 부록 A의 챕터, 관련 질문 번호.
  ```

- 대응 관계가 많은 챕터(ch5, ch6, ch11, ch13, ch16)는 핵심 개념 끝에 **한눈에 보기** 표(다른 언어의 개념 ↔ Rust)를 둡니다.
- **자주 하는 실수**: "다른 언어의 습관이 만드는 실수"를 `compile_fail/`과 연결합니다.
- **연습 문제**: 2~3개. 서술형 챕터(ch1, ch16, ch17)는 "동료에게 설명해 보기" 문제를 허용합니다.
- **참고 자료**: 자료마다 발행일과 확인일(1.5절).

### 2.3 예제

- 예제는 **질문의 답을 눈으로 확인**시키는 용도입니다. 예제 하나가 질문 하나 또는 맞닿은 질문 두세 개를 맡고, 파일 머리 주석에 질문 번호를 적습니다.
- 모든 질문에 예제가 붙을 필요는 없습니다. 근거가 자료인 질문(Q1.3, Q12.4 등)은 자료로 답합니다. 다만 README의 주장 가운데 실행으로 확인할 수 있는 것은 예제나 `compile_fail/`로 뒷받침합니다.
- 분량: 예제 3~6개, `compile_fail` 2~5개. 큰 챕터(ch9)는 예제 8개까지. README는 300~700줄, 질문 하나에 30~60줄.

### 2.4 다른 언어의 코드

**C와 C++** 는 파일로 두고 실제로 컴파일해 확인합니다. 2026-11-21에 이 환경에서 Apple clang 21.0.0의 AddressSanitizer(해제 후 사용 검출)와 ThreadSanitizer(데이터 경쟁 검출)가 동작하는 것을 임시 파일로 확인했습니다.

- 위치는 챕터의 `compare/`입니다. Cargo가 빌드 대상으로 보지 않으므로 워크스페이스에 영향이 없습니다.
- 파일 머리 주석에 보여 주는 것, 컴파일·실행 명령, 기대하는 결과를 적습니다.

  ```sh
  cc  -g -fsanitize=address,undefined -o target/tmp/<패키지>/<이름> <챕터>/compare/<파일>.c
  c++ -std=c++20 -g -fsanitize=address,undefined -o target/tmp/<패키지>/<이름> <챕터>/compare/<파일>.cpp
  cc  -g -fsanitize=thread -o target/tmp/<패키지>/<이름> <챕터>/compare/<파일>.c      # 데이터 경쟁
  ```

- 미정의 동작이 있는 프로그램은 실행할 때마다, 컴파일러마다 결과가 다릅니다. **새니타이저 없이 실행한 출력은 싣지 않고**, 새니타이저가 보고한 오류 종류 한 줄(`heap-use-after-free` 등)만 인용합니다. 주소와 스택 추적은 싣지 않습니다. 결과가 정해지지 않는다는 점 자체가 설명할 내용입니다.
- 결과가 정해져 있는 코드(매크로 인자의 중복 평가, 부호 있는 수와 없는 수의 비교)는 출력을 그대로 적습니다.
- README에 확인한 컴파일러와 운영체제를 밝힙니다. 다른 컴파일러(GCC, MSVC)에서는 옵션과 메시지가 다릅니다.
- 비교 코드는 표준 라이브러리만 쓰고 몇 초 안에 끝나며 파일과 네트워크를 건드리지 않습니다.
- 확인할 것: Apple clang이 LeakSanitizer를 지원하는지, `-std=c++23`이 되는지.

**Java, C#, Go, Python, JavaScript/TypeScript** 는 README 안의 10줄 이하 조각으로만 싣습니다. 그 언어의 널리 알려진 동작을 떠올리게 하는 용도이며, 출력은 적지 않고 해당 언어 공식 문서를 근거로 링크합니다. 조각이 맞는지 확신할 수 없으면 코드 대신 문장으로 씁니다. 이 언어들의 코드는 파일로 두지 않고 실행해 확인하지도 않습니다(9절).

비교는 공정하게 합니다. 그 언어의 요즘 관용구(C++의 스마트 포인터와 범위 기반 `for`, Java의 `Optional`과 try-with-resources, Go의 `defer`)를 쓰고, 일부러 서툴게 쓴 코드를 세워 두고 비교하지 않습니다.

## 부록 B 공통
- 독자: 다른 언어(C/C++, Java, C#, Go, Python, JS/TS)를 실무에서 써 봤고 Part 0을 마친 사람입니다.

  그 언어의 요즘 관용구와 비교합니다. 홍보 문구("blazingly fast" 류)를 쓰지 않습니다.

  성능 수치를 지어내지 않습니다.
- C/C++ 비교 코드: compare/에 두고 새니타이저를 켜서 컴파일·실행해 확인합니다.

## 8. 검증과 마무리

챕터별 검증은 `/writing-guide` 3절과 5절 그대로입니다(패키지 이름만 `faq-ch…`). 부록 B에서 더 봅니다.

- **자체 검증에 추가**: `compare/` 파일마다 머리 주석의 명령으로 컴파일·실행해 기대한 새니타이저 보고가 나오는지. 산출물은 `target/tmp/<패키지>`에.
- **검증 요청의 "실행 방법"에 추가**: `compare/` 파일별 명령과 기대 결과.
- **reviewer에게 더 볼 것으로 요청**: 인용한 수치와 날짜를 출처 페이지에서 다시 확인, 다른 언어에 대한 서술이 그 언어 공식 문서와 맞는지, 짧은 답만 읽어도 답이 되는지, 질문마다 한계나 비용이 빠지지 않았는지, 참고한 자료의 본문이나 코드를 옮긴 곳이 없는지.

범위를 모두 마친 뒤:

- `cargo fmt --all --check`, `cargo build --workspace --examples`, `cargo clippy --workspace --examples -- -D warnings`, `(cd web && pnpm build)`
- 부록 README의 질문 색인이 챕터 README의 질문 표와 일치하는지, 로드맵과 `PROGRESS.md`의 숫자가 맞는지 확인합니다.
- 이름으로만 가리킨 부록 B 챕터를 상대 링크로 바꿉니다. 본편과 부록 A의 관련 챕터에서 부록 B로 가는 링크를 걸지 정합니다(예: Part 0 ch4 → ch4).
- `SHARED.md`에 옮깁니다: 새 용어(아래 후보), 시점에 기대는 사실과 확인일(2.5절), 미작성 파트가 이어받을 내용(Part 8 `ch8`, Part 9 `ch10`, Part 10 `ch12`와 서로 링크).

용어 후보(처음 쓰는 챕터에서 "용어 메모"에 확정): memory safety 메모리 안전성 / spatial·temporal 공간적·시간적 / undefined behavior 미정의 동작 / garbage collector 가비지 컬렉터(GC) / bounds check 경계 검사 / soundness 건전성 / exception 예외 / interface 인터페이스 / type erasure 타입 소거 / destructive move 파괴적 이동 / sanitizer 새니타이저 / supply chain 공급망. 이미 정한 표기(비용 없는 추상화, 데이터 경쟁, 댕글링 참조, 해제 후 사용, 이중 해제, 단형성화)는 그대로 씁니다.
