# writing guide

@docs/roadmap.md 의 챕터를 설명 문서(README.md)와 실습 예제로 정리합니다.
사용자는 작업할 범위(어느 파트의 어느 챕터까지)를 전달합니다.

요청한 범위의 챕터를 메인 세션이 로드맵 순서대로 하나씩 직접 작성합니다. 챕터 하나를 쓰면 @.claude/agents/reviewer.md 에게 검증을 맡기고, 검증을 통과해야 다음 챕터를 시작합니다.

## 역할 나누기

- **메인 세션이 씁니다.** 앞 챕터에서 무엇을 어떤 용어로 어디까지 설명했고 무엇을 뒤로 미뤘는지가 다음 챕터의 전제입니다. 한 세션이 이어서 써야 이 맥락이 끊기지 않습니다. 챕터 작성을 서브 에이전트에게 넘기지 않습니다.
- **reviewer가 검증합니다.** 쓴 사람은 자기가 아는 것을 독자도 안다고 여기기 쉽고, 자기가 확인했다고 믿는 사실을 다시 의심하지 않습니다. reviewer는 기억 없이 시작하므로 독자와 같은 자리에서 읽고, 챕터의 사실을 실제 툴체인과 기준 문서에 다시 대조합니다.
- **교정은 다시 메인 세션이 합니다.** reviewer는 저장소 파일을 고치지 않고 지적만 보고합니다. 무엇을 왜 고쳤는지가 메인 세션의 맥락에 남아야 다음 챕터에 이어지기 때문입니다.
- **한 번에 한 챕터만 진행합니다.** 여러 챕터를 동시에 쓰거나, 검증이 끝나지 않은 챕터를 두고 다음 챕터를 시작하지 않습니다.

범위가 길면 대화 문맥이 중간에 요약될 수 있습니다. 챕터를 넘어 이어져야 하는 것(정한 용어, 뒤로 미룬 내용, 겪은 함정)은 기억에 맡기지 말고 챕터가 끝날 때마다 `SHARED.md`에 적습니다(6절). 문맥이 요약된 뒤에는 이 문서, `SHARED.md`, 직전 챕터의 README를 다시 읽고 이어 갑니다.

## 1. 범위 확정

- 사용자가 준 범위를 로드맵의 챕터 목록으로 풉니다. `PROGRESS.md`에서 이미 ✅인 챕터는 건너뜁니다.
- 범위가 없거나 모호하면 `PROGRESS.md`에서 다음 미완료 구간을 찾아 제안하고 확인을 받습니다. 챕터마다 작성과 검증 루프를 거치는 큰 작업이라 범위를 짐작으로 정하지 않습니다.
- 로드맵의 해당 파트 머리말에 있는 "준비" 항목을 읽습니다. 툴체인·타깃·도구 설치처럼 사용자 환경을 바꾸는 준비물이 있으면 시작 전에 사용자에게 묻습니다. 승인받지 못한 준비물이 필요한 부분은 설명만 쓰고, 검증하지 못했다고 README에 밝히고 사용자에게 알립니다.
- `rustc --version`, `cargo --version`을 확인합니다. 챕터에 적을 값이고 reviewer에게도 알려 줍니다.
- `SHARED.md`의 "작업 방식 메모", "후속 조치", "용어 메모"를 읽습니다. 이 저장소에서 이미 겪은 함정과 앞 파트가 이 범위로 넘긴 숙제가 쌓여 있습니다.
- 범위의 첫 챕터와 내용이 이어지는 완성된 챕터(같은 파트의 직전 챕터, 로드맵이 선수 과정으로 적은 챕터)의 README를 읽어 용어와 설명 수준을 맞춥니다.

## 2. 파트 준비

새 파트를 시작할 때 한 번 합니다.

- 파트 README(`partN-slug/README.md`)를 만듭니다. 구성은 `part0-getting-started/README.md`를 따릅니다: 파트 개요, 학습 방법, 챕터 목차 표(완료된 챕터만 행으로 추가).
- `PROGRESS.md`에 파트 표를 추가합니다. 열은 Part 0 표와 같게 `상태 | 챕터 | 산출물 | 완료일`로 하고, 요약 표에도 행을 나눠 적습니다.

## 3. 챕터 작성

챕터마다 아래 순서로 진행합니다. 지켜야 할 기준은 4절에 있습니다.

1. **계획**: 로드맵의 해당 행(학습 주제, 예제 계획, 기준 문서 절)에 다음을 더해 이 챕터가 다룰 것을 정합니다.
   - 이어받을 내용: 앞 챕터들이 "이 챕터에서 다룬다"고 미룬 것. `SHARED.md`의 "후속 조치"와 앞 챕터 README에서 찾습니다. 빠뜨리면 앞 챕터의 약속이 지켜지지 않습니다.
   - 미룰 내용: 뒤 챕터나 다른 파트가 맡을 주제와 그 챕터 이름. 정해 두지 않으면 챕터마다 같은 내용을 반복해 설명하게 됩니다.
   - 분량: 예제 수의 상한. 정하지 않으면 개념마다 파일을 나눠 10개를 넘기기 쉽습니다.
2. **레퍼런스 읽기**: 로드맵 "기준 문서 절"의 해당 절을 직접 열어 읽습니다.
3. **설계**: 학습 목표를 3~5개로 정하고, 목표마다 그것을 눈으로 확인시켜 줄 예제를 대응시킵니다. 예제로 뒷받침되지 않는 목표나, 어떤 목표에도 속하지 않는 예제가 없게 합니다.
4. **디렉터리 준비**: 챕터 디렉터리에 `Cargo.toml`(로드맵 2.3절의 기본형)과 첫 예제 파일을 연달아 만들고, 그 뒤에 cargo를 실행합니다. 루트 워크스페이스가 `members = ["part*/ch*", "appd-*/ch*"]`라서 `Cargo.toml`이 없거나 빌드 타깃이 하나도 없는 챕터 디렉터리가 있으면 워크스페이스 전체의 cargo 명령이 실패합니다. 주 실습이 `projects/` 아래 독립 프로젝트인 챕터도 같은 이유로 `examples/*.rs`가 최소 하나는 있어야 합니다.
5. **예제 작성**: 하나씩 작성하고 바로 실행해 출력을 확인합니다.
6. **README 작성**: 확정된 예제와 실제 출력을 바탕으로 씁니다.
7. **자체 검증**: reviewer에게 넘기기 전에 직접 통과시킵니다. 검증 한 번은 비용이 크므로, 명령만 돌려도 잡히는 문제를 reviewer가 찾게 두지 않습니다. 마지막 수정 이후에 다시 실행한 결과만 유효합니다.

   ```sh
   cargo fmt -p <패키지> --check
   cargo build -q -p <패키지> --examples
   cargo clippy -q -p <패키지> --examples -- -D warnings
   cargo run -q -p <패키지> --example <이름>     # 예제마다. 출력을 `// 출력:` 주석·README와 대조
   rustc --edition 2024 --out-dir <임시 디렉터리> <챕터>/compile_fail/<파일>.rs   # 파일마다, 기대한 에러 코드인지
   ```

   - `projects/` 아래 프로젝트는 그 디렉터리에서 `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, 실행을 확인하고 `cargo clean`으로 정리합니다.
   - 예제 안에 `#[cfg(test)]` 테스트가 있으면 `cargo test -p <패키지> --examples`도 실행합니다.
   - README에 적은 실행 명령, 출력, 파일 링크가 최종 파일과 일치하는지 다시 대조합니다. 예제를 고친 뒤 README의 출력을 그대로 두는 실수가 가장 흔합니다.
   - 남은 것이 없는지 봅니다: 챕터 디렉터리 안의 빌드 산출물, 띄워 둔 프로세스, 루트 `Cargo.toml`의 변경.
   - 임시 파일과 `rustc --out-dir` 산출물은 `target/tmp/<패키지>`에 둡니다.

## 4. 챕터 작성 규칙

메인 세션이 챕터를 쓸 때 지키는 기준이고, reviewer가 챕터를 검증할 때 쓰는 기준이기도 합니다. 디렉터리 구조, 이름 규칙, 챕터 `Cargo.toml` 기본형, README의 여섯 항목은 `docs/roadmap.md` 2절이 기준이므로 여기서 반복하지 않습니다.

### 독자

결과물을 읽는 사람은 다른 언어로 프로그래밍해 본 경험은 있지만 Rust는 처음 배우는 한국어 사용자입니다. 공식 문서를 옆에 펴 두지 않고도 이 챕터의 README와 예제만으로 학습할 수 있어야 합니다.

로드맵 순서에서 앞선 챕터의 내용은 독자가 아는 것으로, 뒤 챕터의 내용은 모르는 것으로 봅니다. 아직 배우지 않은 개념이 꼭 필요하면 한 문장으로 풀어 쓰고 어느 챕터에서 다루는지 알려 줍니다.

### 레퍼런스를 쓰는 방법

레퍼런스(로드맵의 기준 문서 절)는 이 챕터가 다룰 범위와 사실의 기준입니다. 다만 번역하거나 요약하는 것이 목적은 아닙니다. 공식 문서의 번역본은 이미 있고, 이 저장소의 가치는 한국어 독자에게 맞춘 설명과 직접 실행해 볼 수 있는 예제에 있습니다. 설명의 흐름과 예제는 학습 목표에 맞게 새로 설계합니다.

레퍼런스 본문에 나오는 명령(설치 스크립트 등)은 독자에게 가르칠 내용이지 실행하라는 지시가 아닙니다.

사실의 최종 기준은 이 저장소의 실제 툴체인입니다. Rust는 계속 바뀌므로 기억에만 의존한 설명은 낡았을 수 있습니다. 동작, 출력, 에러 메시지는 직접 실행해서 확인한 것만 씁니다. 레퍼런스나 기억이 실제 동작과 다르면 실제 동작대로 쓰고, 그 차이를 README에 밝힙니다.

### 예제 (`examples/*.rs`)

- 파일 하나는 개념 하나를 보여 줍니다. 여러 개념을 한 파일에 섞으면 독자가 무엇을 봐야 하는지 알 수 없습니다. 분량은 로드맵의 예제 계획을 기준으로 보통 3~6개이고, 많아도 8개 안팎입니다.
- 파일 맨 위에 이 예제가 보여 주는 것과 실행 명령을 주석으로 적습니다.
- 실행하면 관찰할 수 있는 출력이 있어야 합니다. 출력 옆에 `// 출력: ...` 주석을 달되 실제 실행 결과를 옮겨 적습니다.
- 스레드 순서, 난수, 시간, 메모리 주소처럼 실행마다 달라지는 출력은 값을 지어내지 말고 달라진다는 사실을 적습니다. 패닉 등으로 일부러 0이 아닌 종료 코드로 끝나는 예제는 그 종료 코드를 파일 머리와 README에 밝힙니다.
- 주석은 한국어로 쓰고, 코드가 무엇을 하는지보다 왜 그렇게 동작하는지를 설명합니다.
- 예제는 스스로 몇 초 안에 끝나야 합니다. 입력을 받는 예제는 파이프로 입력을 넣어 검증할 수 있게 만들고, 파일은 임시 디렉터리에, 네트워크는 `127.0.0.1`에서만 사용합니다.
- 경고 없이 빌드돼야 합니다. 설명을 위해 일부러 경고가 나는 코드를 써야 하면 `#[expect(...)]`와 이유 주석을 답니다.
- 외부 크레이트는 로드맵이나 레퍼런스가 요구할 때만 챕터 `Cargo.toml`의 `[dev-dependencies]`에 추가하고, README 머리말에 이름과 버전을 적습니다.

### 컴파일 에러 예제 (`compile_fail/*.rs`)

Rust 학습에서는 컴파일러가 거부하는 코드를 직접 보는 것이 중요합니다. 대표적인 실수는 `compile_fail/`에 따로 둡니다.

- 파일 맨 위에 기대하는 에러 코드와 핵심 메시지를 주석으로 적습니다.
- `rustc --edition 2024`로 컴파일해 **실제로 그 에러 코드로 실패하는지** 확인합니다. 대여 검사기가 개선되면서 예전에는 에러였던 코드가 지금은 통과하는 경우가 있습니다. 통과해 버리는 "에러 예제"는 독자를 혼란에 빠뜨립니다.
- 컴파일 산출물이 챕터 디렉터리에 남지 않도록 `--out-dir`로 임시 디렉터리를 지정합니다.
- 앞 챕터에 이미 있는 것과 같은 에러 코드·같은 상황은 피하고, 필요하면 그 챕터를 가리킵니다.
- README에는 에러 메시지의 핵심 부분을 그대로 인용하고, 읽는 법과 고치는 방법을 설명합니다.

### 독립 프로젝트 (`projects/*`)

여러 파일로 이뤄진 프로그램, 다른 에디션이나 타깃, Cargo 자체를 다루는 실습에만 사용합니다.

- 프로젝트의 `Cargo.toml`에 빈 `[workspace]` 테이블을 넣어 루트 워크스페이스와 분리하고, 해당 디렉터리 안에서 빌드·테스트해 검증합니다.
- 저장소 밖 임시 디렉터리에서 만든 뒤 복사합니다. 저장소 안에서 `cargo new`를 실행하면 루트 `Cargo.toml`의 `members`가 조용히 바뀝니다. 작업 뒤 루트 `Cargo.toml`이 바뀌지 않았는지 확인합니다.
- 앞 챕터의 프로젝트를 이어서 발전시키는 챕터는 그 프로젝트를 자기 디렉터리로 복사해서 고치고, 앞 챕터 디렉터리는 건드리지 않습니다.
- 일부러 실패하는 패키지나 기능 조합이 여럿이면 README에 "디렉터리, 명령, 기대 결과"를 표로 적습니다.

### 설명 문서 (`README.md`)

구성은 `docs/roadmap.md` 2.4절의 여섯 항목을 따릅니다. 항목별로 지킬 점은 다음과 같습니다.

- **제목**: 첫 줄은 `# ch{N}. 제목` 형식이고, `ch{N}. `과 백틱을 포함해 30자를 넘기지 않습니다. 이 제목은 사이트 사이드바와 예제 페이지마다 붙는 돌아가기 링크에 그대로 쓰이므로, 길면 잘리거나 여러 줄로 꺾입니다. 주제 이름만 쓰거나 "주제: 짧은 부제"까지만 씁니다. 다루는 타입·명령·세부 주제를 나열하지 않습니다. 그런 목록은 파트 README 챕터 목차의 "주제" 칸과 학습 목표에 둡니다. 예: `ch9. 입출력·파일·경로`, `ch12. 입출력 프로젝트: minigrep 만들기`. 피할 예: `ch9. 입출력·파일·경로: Read/Write/BufRead/Seek, std::fs, Path/PathBuf`.
- **학습 목표**: "~을 설명할 수 있다", "~을 작성할 수 있다"처럼 독자가 스스로 확인할 수 있는 문장으로 씁니다.
- **핵심 개념**: 규칙만 나열하지 말고 그 규칙이 왜 있는지, 어떤 문제를 막는지 설명합니다. Rust의 규칙은 이유를 알아야 납득되고 기억에 남습니다. 다른 언어와의 비교는 이해에 도움이 될 때만 씁니다. 코드는 핵심 부분만 짧게 싣고, 전체는 `examples/` 파일로 연결합니다.
- **예제 안내**: 파일별로 무엇을 보여 주는지, 실행 명령, 기대 출력을 적습니다. 출력은 실제 실행 결과를 옮깁니다.
- **자주 하는 실수**: `compile_fail/` 파일과 연결해 에러 메시지, 원인, 해결 방법 순서로 씁니다.
- **연습 문제**: 이 챕터까지 배운 것만으로 풀 수 있는 과제 2~4개를 냅니다. 문제마다 접힌 힌트(`<details>`)를 답니다.
- **참고 자료**: 레퍼런스에 있었거나 직접 열어 확인한 링크만 싣습니다.

### 문체, 용어, 표기

- 평서형 존댓말("~합니다")로 쓰고, 완결된 문장으로 설명합니다.
- 용어는 `SHARED.md` "용어 메모"의 표기를 따르고(소유권, 대여, 라이프타임, 트레이트 등), 챕터에서 처음 나올 때 영어를 병기합니다. 예: 소유권(ownership). 같은 대상은 끝까지 같은 용어로 부릅니다.
- 키워드, 타입, 함수, 명령은 번역하지 않고 코드 서식으로 씁니다.
- 분량을 채우기 위한 문장은 넣지 않습니다. 학습 목표를 모두 다뤘으면 충분합니다.
- 저장소 챕터는 `ch8` 형식으로 부릅니다. "8장" 같은 표기는 기준 문서의 장을 가리킬 때만 씁니다. 저장소 챕터 번호와 기준 문서의 장 번호가 다른 파트가 있기 때문입니다.
- 이미 완성된 챕터는 상대 링크를 걸고, 아직 없는 챕터는 링크 없이 코드 서식의 이름으로만 적습니다. 없는 파일을 가리키는 링크는 사이트 빌드에서 경고가 납니다.
- 챕터는 사이트에 그대로 게시됩니다. 개인 경로(홈 디렉터리 등)가 출력이나 본문에 실리지 않게 합니다.

### 환경을 바꾸는 작업

툴체인이나 타깃 설치, `cargo install`, 패키지 관리자 사용처럼 사용자 환경을 바꾸는 작업은 사용자가 승인한 것만 합니다. 필요한 도구가 없으면 가능한 부분까지 쓰고, 검증하지 못한 부분과 필요한 준비물을 README에 밝히고 사용자에게 알립니다.

## 5. 검증과 교정 루프

자체 검증까지 마친 챕터를 reviewer에게 넘기고, 통과 판정을 받을 때까지 교정합니다.

### 검증 요청

`Agent` 도구로 `reviewer`를 호출합니다. reviewer가 아는 것은 `reviewer.md`와 요청 메시지, 저장소의 파일뿐입니다. 아래 뼈대를 채워 보냅니다.

```
## 대상 챕터
- 디렉터리: <절대 경로>
- 패키지 이름: <p{파트}-ch{챕터}-{slug}>
- 로드맵 위치: <파트와 챕터, 로드맵 행의 학습 주제·예제 계획·기준 문서 절>

## 환경
- 확인한 rustc/cargo 버전
- 임시 디렉터리: <루트>/target/review/<패키지 이름>
- 설치돼 있지 않아 쓸 수 없는 도구·툴체인·타깃

## 이 챕터의 계획
- 이어받은 내용: <앞 챕터가 이 챕터로 미룬 것>
- 미룬 내용: <뒤 챕터 이름과 주제>
- 로드맵·기준 문서와 일부러 다르게 쓴 것과 이유

## 실행 방법
- 예제마다: 표준 입력, 인자, 기대 종료 코드(0이 아닌 것), 실행마다 달라지는 줄
- compile_fail 가운데 `rustc --edition 2024` 말고 다르게 컴파일해야 하는 파일
- projects: "디렉터리, 명령, 기대 결과" 표

## 레퍼런스
- <로드맵 "기준 문서 절"에 해당하는 URL>
```

요청에는 실행 방법과 의도만 적고 결론은 적지 않습니다. "검증을 모두 통과했다", "이 설명은 확인한 사실이다" 같은 말을 넘기면 reviewer가 그것을 다시 확인하지 않고 받아들이기 쉽습니다. 챕터가 주장하는 사실은 README에 있는 것으로 충분합니다.

reviewer가 도는 동안에는 대상 챕터와 워크스페이스를 고치지 않고 cargo도 실행하지 않습니다. reviewer는 그 시점의 파일을 실행해 대조하고 있으므로, 도중에 바뀌면 보고를 믿을 수 없게 됩니다.

### 보고를 받은 뒤

보고의 판정은 "통과" 또는 "수정 필요"입니다. "반드시 고칠 것"이 하나도 없어야 통과입니다.

- **반드시 고칠 것**: 지적마다 직접 재현해 확인한 뒤 고칩니다. reviewer도 틀릴 수 있습니다. 재현되지 않거나 지적이 틀렸다고 판단하면 고치지 않고, 근거(실행한 명령과 출력, 문서의 위치)를 재검증 요청에 적습니다. 사실에 대한 의견이 갈리면 실제 툴체인의 동작이 기준입니다.
- **권장**: 반영할지 판단합니다. 반영하지 않으면 이유를 한 줄 적어 알립니다. 권장은 통과를 막지 않습니다.
- 고친 뒤에는 3절의 자체 검증을 다시 돌립니다. 예제를 고쳤으면 README의 해당 출력도 함께 고칩니다.

### 재검증

같은 reviewer에게 `SendMessage`로 다시 요청합니다. 자기가 지적한 것을 알고 있어 수정이 맞는지 바로 확인할 수 있습니다. 메시지에는 다음을 적습니다.

- 지적 번호마다: 고침(무엇을 어떻게) 또는 고치지 않음(근거)
- 바뀐 파일 목록

그 reviewer에게 더는 메시지를 보낼 수 없으면(세션이 다시 시작된 경우 등) 새 reviewer를 호출하고, 원래 요청에 이전 보고와 처리 내용을 붙입니다.

### 루프를 끝내는 조건

- **통과**: 6절로 넘어갑니다.
- **세 번째 보고까지 "수정 필요"**: 첫 검증을 포함해 보고를 세 번 받고도 통과하지 못하면 네 번째를 요청하지 않고 멈춥니다. 다음 챕터로 넘어가지 않고 커밋도 하지 않습니다. `PROGRESS.md`의 챕터 상태는 🔄로 두고, 사용자에게 남은 지적과 메인 세션·reviewer 양쪽의 근거, 고를 수 있는 선택지를 보고합니다. 뒤 챕터가 이 챕터에 기대므로, 풀리지 않은 지적을 안은 채 진행하지 않습니다.

## 6. 통과한 뒤

세 곳을 함께 갱신합니다.

- `PROGRESS.md`: 챕터 행을 ✅로 바꾸고 산출물(`예제 N / 에러 N / 프로젝트 N`)과 완료일을 채웁니다. 요약 표의 숫자와 머리말의 "다음 작업"도 고칩니다. 이 문서에는 어디까지 진행됐는지만 적습니다. 로드맵·기준 문서와 달라진 점, 일부러 실패하거나 실행마다 달라지는 예제, 추가한 외부 크레이트, 메인 세션과 reviewer 모두 확인하지 못한 것은 챕터 README에 밝히고 사용자에게 알립니다.
- `docs/roadmap.md`: 상태 칸과 4절 진행 현황의 숫자.
- 파트 README: 챕터 목차에 행 추가.

다음 챕터와 다음 세션을 위해 `SHARED.md`에 옮겨 적습니다. 직접 겪은 것과 reviewer의 보고 양쪽에서 가져오되, 모든 챕터가 함께 봐야 하는 것만 적습니다. 이 챕터에만 해당하는 것은 README에 둡니다.

- 새로 정한 용어 → "용어 메모". 이미 있는 표기와 다르면 먼저 쓴 쪽이나 더 많은 챕터가 쓰는 쪽으로 정하고 어긋난 챕터를 고칩니다.
- 다음 작업자가 피해야 할 함정(lint, 도구 동작, 기억이나 레퍼런스와 달랐던 툴체인 동작) → "작업 방식 메모".
- 이 챕터가 뒤로 미룬 내용과 맡을 챕터, 다른 파트나 파일에 반영할 일 → "후속 조치".

`PROGRESS.md`와 `SHARED.md`에는 개인 경로나 세션 내부 식별자를 적지 않습니다.

마지막으로 챕터 하나를 커밋 하나로 남깁니다. 이 챕터가 바꾼 파일(챕터 디렉터리, `PROGRESS.md`, `SHARED.md`, `docs/roadmap.md`, 파트 README, `Cargo.lock`)만 골라 담고, 메시지는 `add part3 ch1-getting-started`처럼 파트와 챕터 디렉터리 이름을 적습니다. push는 사용자가 직접 합니다.

그다음 3절로 돌아가 다음 챕터를 시작합니다.

## 7. 범위를 마친 뒤

- 독자가 실행할 방식으로 전체를 확인합니다.

  ```sh
  cargo fmt --all --check
  cargo build --workspace --examples
  cargo clippy --workspace --examples -- -D warnings
  (cd web && pnpm build)      # "[sync-content] … 링크 대상이 없습니다" 경고가 없어야 합니다
  ```

- 챕터 사이를 훑습니다: 용어 메모와 다른 표기, 기준 문서의 장이 아닌데 "N장"으로 쓴 곳, 뒤 챕터가 "앞에서 배웠다"고 한 내용이 실제로 앞 챕터에 있는지. 앞 챕터가 이름으로만 가리켰던 뒤 챕터가 이번 범위에서 생겼으면 상대 링크로 바꿉니다.
- 임시 디렉터리(`target/tmp`, `target/review`)를 지웁니다.
- 이 단계에서 고친 것이 있으면 커밋을 하나 더 만듭니다.

## 부록(`appd-*`)을 쓸 때

부록은 본편(Part 0~11)과 별도인 파트이며 위 절차를 그대로 따릅니다. 다른 점만 적습니다.

- 범위 표기: `/writing-guide appd-a ch1~ch9`. 부록 A(Effective Rust)의 챕터 계획은 `docs/roadmap.md` 3절의 "부록 A"에, 챕터별 작성 메모(본편 연결, 주의·준비물)는 `plan/plan-effective-rust.md` 4절에 있습니다. 그 계획서의 "위임", "tutor", 동시 실행에 관한 내용은 예전 작업 방식이므로 이 문서를 따릅니다.
- 디렉터리는 `appd-a/ch{N}-{slug}`(N은 책의 Item 번호), 패키지 이름은 `er-ch{N}-{slug}`입니다.
- 워크스페이스의 `"appd-*/ch*"` 글롭은 맞는 디렉터리가 하나도 없으면 cargo가 실패합니다. 부록의 첫 챕터 디렉터리를 만든 뒤에 `members`에 추가합니다.
- `plan/plan-effective-rust.md` 6절의 "부록 공통" 블록을 4절의 작성 규칙에 더해 적용하고, 검증 요청에도 그대로 넣습니다. 4절은 독자를 Rust 입문자로 가정하므로, 독자가 Part 0·1을 마친 사람이라는 점과 저작권 조건(번역·발췌·코드 인용 금지)은 꼭 넣습니다. 챕터별 조건은 계획서 4절 작성 메모와 1.4절 표에서 옮깁니다.
- 책에 없는 판단 기준을 지침으로 더했으면 README의 "책과 달라진 점"에 "책에 없는 지침"으로 밝힙니다.
- 검증 요청에 부록에서 더 볼 것을 적습니다: README에 책 본문을 옮긴 문단이나 책의 코드와 같은 예제가 없는지, 지침 목록을 책의 해당 Item과 대조해 "책에 없는 지침" 표시가 맞는지, "책과 달라진 점"에 적힌 동작이 다시 실행해도 그대로인지.
- 진척은 본편 합계(109)와 따로 셉니다. `PROGRESS.md`와 로드맵 4절의 부록 행, 부록 README의 목차(책의 장별로 묶음)를 갱신합니다.

## 사용자에게 알릴 것

reviewer의 보고는 사용자에게 보이지 않습니다. 챕터가 끝날 때마다 짧게, 범위가 끝나면 모아서 다음을 전합니다.

- 무엇을 만들었는지(예제·에러 예제·프로젝트 수)와 커밋
- 검증을 몇 번 거쳤는지, reviewer가 찾아 고친 것 가운데 내용에 영향을 준 것
- 로드맵이나 기준 문서와 다르게 쓴 부분과 그 이유
- 확인하지 못한 것(다른 운영체제, 설치하지 않은 도구가 필요한 검증 등)
- 사용자가 정해야 할 것(세 번째 보고까지 통과하지 못한 챕터, 분량 조정, 환경 준비 승인 등)
