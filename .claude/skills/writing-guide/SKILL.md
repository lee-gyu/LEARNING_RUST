# writing guide

@docs/roadmap.md 의 챕터를 설명 문서(README.md)와 실습 예제로 정리합니다.
사용자는 작업할 범위(어느 파트의 어느 챕터까지)를 전달합니다.

요청한 범위의 챕터를 @.claude/agents/tutor.md 에게 하나씩 위임해서 작성합니다.

## 역할 나누기

챕터 하나를 쓰는 일은 tutor가 맡고, 이 스킬을 실행하는 메인 세션은 챕터 사이의 일을 맡습니다. tutor는 호출마다 기억 없이 시작하고 자기 챕터 디렉터리 밖은 고치지 못합니다. 그래서 다음 일은 메인 세션이 하지 않으면 아무도 하지 않습니다.

- 챕터마다 무엇을 다루고 무엇을 미룰지 정해 위임 메시지에 담기
- tutor의 결과를 직접 다시 검증하기
- `PROGRESS.md`, `docs/roadmap.md`, 파트 README 갱신하기
- 챕터 사이의 용어·표기를 맞추기

챕터 본문과 예제는 직접 쓰지 않습니다. 검증에서 드러난 문제는 그 챕터의 tutor에게 다시 보내 고치게 하고, 용어 한 군데처럼 작은 표기 수정만 직접 합니다.

## 1. 범위 확정

- 사용자가 준 범위를 로드맵의 챕터 목록으로 풉니다. `PROGRESS.md`에서 이미 ✅인 챕터는 건너뜁니다.
- 범위가 없거나 모호하면 `PROGRESS.md`에서 다음 미완료 구간을 찾아 제안하고 확인을 받습니다. 챕터 하나에 에이전트 하나를 쓰는 큰 작업이라 범위를 짐작으로 정하지 않습니다.
- 로드맵의 해당 파트 머리말에 있는 "준비" 항목을 읽습니다. 툴체인·타깃·도구 설치처럼 사용자 환경을 바꾸는 준비물이 있으면 시작 전에 사용자에게 묻습니다. 승인받지 못한 준비물이 필요한 부분은 "설명만 쓰고 검증하지 못했다고 밝힌다"는 조건으로 위임합니다.
- `rustc --version`, `cargo --version`을 확인합니다. tutor에게 알려 줄 값입니다.
- `PROGRESS.md`의 "작업 방식 메모", "후속 조치", "용어 메모"를 읽습니다. 이 저장소에서 이미 겪은 함정과 앞 파트가 이 범위로 넘긴 숙제가 쌓여 있습니다.

## 2. 파트 준비

새 파트를 시작할 때 한 번 합니다.

- 파트 README(`partN-slug/README.md`)를 만듭니다. 구성은 `part0-getting-started/README.md`를 따릅니다: 파트 개요, 학습 방법, 챕터 목차 표(완료된 챕터만 행으로 추가).
- `PROGRESS.md`에 파트 표를 추가합니다. 열은 Part 0 표와 같게 `상태 | 챕터 | 산출물 | 검증 | 완료일 | 비고`로 하고, 요약 표에도 행을 나눠 적습니다.

## 3. 챕터 디렉터리 준비

위임하기 전에 메인 세션이 챕터 디렉터리를 만들어 둡니다. 루트 워크스페이스가 `members = ["part*/ch*"]`라서, `Cargo.toml`이 없거나 빌드 타깃이 하나도 없는 챕터 디렉터리가 잠깐이라도 생기면 동시에 작업 중인 모든 챕터의 cargo 명령이 실패하기 때문입니다. 완성된 모양을 다른 곳에서 만든 뒤 이름 바꾸기 한 번으로 옮깁니다.

```sh
ROOT=$(git rev-parse --show-toplevel)
part=part1-standard-lib; ch=ch1-std-overview; n=1      # n은 파트 번호
tmp="$ROOT/target/.scaffold"                           # 같은 파일 시스템 안이라 mv가 한 번에 끝납니다
mkdir -p "$tmp/$ch/examples" "$ROOT/$part"
printf '[package]\nname = "p%s-%s"\nversion = "0.0.0"\nedition.workspace = true\npublish.workspace = true\n' "$n" "$ch" > "$tmp/$ch/Cargo.toml"
printf '// 자리표시 파일입니다. 첫 번째 실제 예제를 만든 뒤에 삭제합니다.\nfn main() {}\n' > "$tmp/$ch/examples/00_placeholder.rs"
mv "$tmp/$ch" "$ROOT/$part/$ch"
```

주 실습이 `projects/` 아래 독립 프로젝트인 챕터도 같은 이유로 `examples/*.rs`가 최소 하나는 있어야 합니다. 위임 메시지에 이 점을 적습니다.

## 4. 위임 메시지

tutor가 아는 것은 `tutor.md`와 위임 메시지, 저장소의 파일뿐입니다. 챕터마다 아래 뼈대를 채워 보냅니다. 일관성은 대부분 여기서 결정됩니다.

```
## 대상 챕터
- 디렉터리: <절대 경로>
- 패키지 이름: <p{파트}-ch{챕터}-{slug}>
- 로드맵 위치: <몇 번째 챕터인지, 독자가 이미 아는 것과 아직 모르는 것을 챕터 이름으로>

## 환경과 동시 작업
- 확인한 rustc/cargo 버전, 루트 워크스페이스가 있다는 사실
- 챕터 디렉터리와 자리표시 예제를 만들어 두었다는 것, 자리표시 파일은 첫 실제 예제를 만든 뒤에 지울 것,
  examples/가 한순간도 비면 안 되는 이유
- 지금 함께 작성 중인 챕터 목록
- 전용 빌드 디렉터리: 모든 cargo 명령 앞에 CARGO_TARGET_DIR=<루트>/target/<패키지 이름>
  (독자용 명령에는 붙이지 않음, projects/ 안에서는 쓰지 않고 검증 뒤 cargo clean)
- 전용 임시 디렉터리 경로
- cargo가 다른 챕터의 매니페스트 문제로 실패하면 고치지 말고 다시 시도할 것
- 먼저 읽을 것: PROGRESS.md의 "작업 방식 메모"와 "용어 메모", 이 챕터와 내용이 이어지는 완성된 챕터의 README
- 다른 챕터를 가리키는 방법(아래 "표기 규칙")

## 작성 지침
- 학습 주제: <로드맵 행 그대로>
- 예제 계획: <로드맵 행 그대로>
- 추가 요청: <아래 목록에서 이 챕터에 해당하는 것>

## 레퍼런스
- <로드맵 "기준 문서 절"에 해당하는 URL>
```

"추가 요청"에는 이 챕터에 해당하는 것만 골라 적습니다.

- **이어받을 내용**: 앞 챕터들이 "이 챕터에서 다룬다"고 미룬 것. 앞 챕터 보고의 "다음 챕터를 위한 메모"와 `PROGRESS.md`의 비고·후속 조치에서 찾습니다. 빠뜨리면 앞 챕터의 약속이 지켜지지 않습니다.
- **미룰 내용**: 뒤 챕터나 다른 파트가 맡을 주제와 그 챕터 이름. 적어 주지 않으면 챕터마다 같은 내용을 반복해 설명합니다.
- **분량**: 예제 수의 상한(보통 8개 안팎). 적지 않으면 개념마다 파일을 나눠 10개를 넘기기 쉽습니다.
- **`compile_fail/` 후보**: 에러 코드와 상황을 후보로 주되, 현재 툴체인에서 실제로 그 코드로 실패하는 것만 고르라고 적습니다. 앞 챕터에 이미 있는 것과 같은 코드는 피하게 합니다.
- **실행마다 달라지는 것**: 패닉으로 끝나는 예제, 스레드 순서, 시간, 주소, 난수가 나오는 챕터라면 처리 방법(값을 지어내지 않기, 종료 코드 확인, 몇 초 안에 끝나기).
- **외부 자원**: 추가해도 되는 크레이트와 넣을 위치, 네트워크는 `127.0.0.1`만, 설치해도 되는 도구(승인받은 것만 명시).
- **독립 프로젝트**: 저장소 밖에서 만들어 복사하고 빈 `[workspace]` 테이블을 넣을 것, 작업 뒤 루트 `Cargo.toml`이 바뀌지 않았는지 확인할 것. 저장소 안에서 `cargo new`를 실행하면 루트의 `members`가 조용히 바뀝니다.
- **참고 자료**: 파트의 기준 문서 외에 함께 안내할 자료가 있으면 후보를 주고, 직접 열어 확인한 링크만 싣게 합니다.

표기 규칙(모든 위임 메시지에 넣습니다):

- 저장소 챕터는 `ch8` 형식으로 부릅니다. "8장" 같은 표기는 기준 문서의 장을 가리킬 때만 씁니다. 저장소 챕터 번호와 기준 문서의 장 번호가 다른 파트가 있기 때문입니다.
- 이미 완성된 챕터는 상대 링크를 걸 수 있고, 아직 없거나 작성 중인 챕터는 링크 없이 코드 서식의 이름으로만 적습니다. 없는 파일을 가리키는 링크는 사이트 빌드에서 경고가 납니다.
- 용어는 `PROGRESS.md` "용어 메모"의 표기를 쓰고, 새로 정한 용어는 보고에 적게 합니다.

## 5. 실행 순서

- 한 번에 최대 4개를 같은 메시지에서 띄우고, 하나가 끝나 검증을 마치면 다음 챕터로 빈자리를 채웁니다.
- 로드맵 순서대로 진행합니다. 뒤 챕터는 완성된 앞 챕터의 README를 읽고 수준과 용어를 맞추기 때문입니다.
- 앞 챕터의 산출물을 복사하거나 이어 쓰는 챕터는 그 챕터가 끝나고 검증된 뒤에 시작합니다(예: 한 프로젝트를 챕터마다 발전시키는 파트). 이런 챕터는 앞 챕터의 프로젝트를 자기 디렉터리로 복사해서 고치고, 앞 챕터 디렉터리는 건드리지 않습니다.
- 작성 중인 tutor에게 알려야 할 일이 생기면(용어 변경 등) `SendMessage`로 전합니다.

## 6. 보고를 받은 뒤

tutor의 보고는 그 에이전트가 본 것일 뿐이므로, 챕터마다 직접 다시 확인합니다.

```sh
export CARGO_TARGET_DIR="$ROOT/target/<패키지>"
cargo fmt -p <패키지> --check
cargo build -q -p <패키지> --examples
cargo clippy -q -p <패키지> --examples -- -D warnings
cargo run -q -p <패키지> --example <이름>     # 예제마다. 입력·인자·기대 종료 코드는 보고에 적힌 대로
rustc --edition 2024 --out-dir <임시 디렉터리> <챕터>/compile_fail/<파일>.rs   # 파일마다, 기대한 에러 코드인지
```

- `projects/` 아래 프로젝트는 그 디렉터리에서 `CARGO_TARGET_DIR` 없이 `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, 실행을 확인하고 `cargo clean`으로 정리합니다.
- 예제 안에 `#[cfg(test)]` 테스트가 있으면 `cargo test -p <패키지> --examples`도 실행합니다.
- 남은 것이 없는지 봅니다: 자리표시 파일, 챕터 디렉터리 안의 빌드 산출물, 띄워 둔 프로세스, 루트 `Cargo.toml`의 변경.
- 실패하면 실패한 명령과 출력을 붙여 같은 tutor에게 돌려보냅니다.

통과하면 세 곳을 함께 갱신합니다.

- `PROGRESS.md`: 챕터 행을 ✅로 바꾸고 산출물(`예제 N / 에러 N / 프로젝트 N`), 검증, 완료일, 비고를 채웁니다. 비고에는 사용자가 알아야 할 것만 적습니다: 지침·기준 문서와 달라진 점, 일부러 실패하거나 실행마다 달라지는 예제, 확인하지 못한 것. 요약 표의 숫자도 고칩니다.
- `docs/roadmap.md`: 상태 칸과 4절 진행 현황의 숫자.
- 파트 README: 챕터 목차에 행 추가.

보고에서 다음도 옮겨 적습니다. 다음 챕터의 위임 메시지가 여기서 나옵니다.

- 새로 정한 용어 → "용어 메모". 이미 있는 표기와 다르면 먼저 쓴 쪽이나 더 많은 챕터가 쓰는 쪽으로 정하고, 어긋난 챕터를 고친 뒤 작성 중인 tutor에게 알립니다.
- 다음 작업자가 피해야 할 함정(lint, 도구 동작) → "작업 방식 메모".
- 다른 파트나 파일에 반영할 일 → "후속 조치".

`PROGRESS.md`는 사이트에 그대로 게시됩니다. 개인 경로나 세션 내부 식별자는 적지 않습니다.

## 7. 범위를 마친 뒤

- 독자가 실행할 방식으로 전체를 확인합니다.

  ```sh
  cargo fmt --all --check
  cargo build --workspace --examples
  cargo clippy --workspace --examples -- -D warnings
  (cd web && pnpm build)      # "[sync-content] … 링크 대상이 없습니다" 경고가 없어야 합니다
  ```

- 챕터 사이를 훑습니다: 용어 메모와 다른 표기, 기준 문서의 장이 아닌데 "N장"으로 쓴 곳, 뒤 챕터가 "앞에서 배웠다"고 한 내용이 실제로 앞 챕터에 있는지.
- 챕터별 빌드 디렉터리(`target/p*-ch*`)를 지웁니다.
- 커밋은 사용자가 요청할 때만 합니다.

## 부록(`appd-*`)을 쓸 때

부록은 본편(Part 0~11)과 별도인 파트이며 위 절차를 그대로 따릅니다. 다른 점만 적습니다.

- 범위 표기: `/writing-guide appd-a ch1~ch9`. 부록 A(Effective Rust)의 챕터 계획은 `docs/roadmap.md` 3절의 "부록 A"에, 챕터별 작성 메모(본편 연결, 주의·준비물)와 실행 순서는 `plan/plan-effective-rust.md` 4절과 7절에 있습니다.
- 디렉터리는 `appd-a/ch{N}-{slug}`(N은 책의 Item 번호), 패키지 이름은 `er-ch{N}-{slug}`입니다. 3절의 준비 스크립트에서 `part=appd-a`로 두고 패키지 이름을 `er-$ch`로 씁니다.
- 워크스페이스의 `"appd-*/ch*"` 글롭은 맞는 디렉터리가 하나도 없으면 cargo가 실패합니다. 부록의 첫 챕터 디렉터리를 만든 뒤에 `members`에 추가합니다.
- 위임 메시지에 `plan/plan-effective-rust.md` 6절의 "부록 공통" 요청을 넣습니다. `tutor.md`는 독자를 Rust 입문자로 가정하므로, 독자가 Part 0·1을 마친 사람이라는 점과 저작권 조건(번역·발췌·코드 인용 금지)은 꼭 넣습니다. 챕터별 추가 요청은 계획서 4절 작성 메모와 1.4절 표에서 옮깁니다.
- 진척은 본편 합계(109)와 따로 셉니다. `PROGRESS.md`와 로드맵 4절의 부록 행, 부록 README의 목차(책의 장별로 묶음)를 갱신합니다.
- 위임 메시지의 "추가 요청"에 책에 없는 판단 기준을 넣으면 그대로 챕터의 지침이 됩니다. 책에 없는 지침은 README의 "책과 달라진 점"에 "책에 없는 지침"으로 밝히게 하고, 검증할 때 지침 목록을 책의 해당 Item과 대조합니다.
